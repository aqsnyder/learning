# Network and P2P Layer

## Why This Section Matters

Bitcoin is a peer-to-peer network first. Understanding how nodes discover each other, propagate transactions, and synchronize the blockchain is key to understanding its resilience.

## Prerequisites

- [Section 02 — Protocol Fundamentals](../02-protocol-fundamentals/README.md)

## 🎯 Learning Objectives

After this section you can:
- Describe node types and Bitcoin Core's connection types (outbound full-relay, block-relay-only, feeler, inbound) and audit them on a live node.
- Implement the P2P handshake and header sync in a minimal Python client, handling message framing and checksums.
- Explain transaction relay (inv/getdata, wtxid relay) and compact blocks (BIP 152), estimate their bandwidth, and say what Erlay would change.
- Run mempool-policy experiments (RBF, CPFP, package relay, cluster limits) and distinguish node policy from consensus.
- Analyze eclipse and partition attacks and map each step to Bitcoin Core's mitigations in the source.

## 🛠️ Practice

1. **Census of your own node** — On your mainnet or signet node, tabulate `getpeerinfo` by `connection_type`, `network`, `transport_protocol_type` (v1 vs BIP 324 v2), service flags and user agent, and pull `getnetworkinfo` and `getnodeaddresses`. Compare your user-agent mix with BTC Nodes' current snapshot and explain the differences (inbound vs outbound sampling, Tor). Deliverable: one table plus 150 words on why Core keeps block-relay-only connections alongside full-relay ones. *(~2 h · Bitcoin Core connection types; Mastering Bitcoin ch. 10; BTC Nodes; Grokking Bitcoin ch. 8 (Section 02))*
2. **Bandwidth arithmetic** — Estimate the bytes needed to relay a typical block in full vs as a BIP 152 compact block (80-byte header, nonce, 6-byte short IDs, prefilled coinbase), and the inv traffic to announce one transaction to all your peers. Then measure: snapshot `getpeerinfo`'s `bytesrecv_per_msg` and `bytessent_per_msg` 24 h apart and rank message types by bytes. Explain which cost Erlay (BIP 330) targets and roughly what it could save on your node. *(~2 h · BIP 152; BIP 330; Mastering Bitcoin ch. 10)*
3. **Speak P2P in Python** — Following *Programming Bitcoin* ch. 10, implement the message envelope (magic, command, length, checksum), the version/verack handshake, and `getheaders`/`headers` against your own regtest or signet node (use that network's magic), validating each header's proof-of-work and linkage with your section-02/03 code. Capture the session in Wireshark using its Bitcoin dissector ("Decode As" for non-mainnet ports; your client speaks unencrypted v1). Done when you sync every header from your node and Wireshark decodes each message you send. *(~4 h · Programming Bitcoin ch. 10 (Section 02); Bitcoin Developer Guide: P2P Network)*
4. **Mempool-policy lab** — On regtest with Bitcoin Core ≥ 31 (cluster mempool): (a) replace a transaction with `bumpfee` and inspect what was evicted; (b) build a low-fee parent plus a high-fee child and read its cluster and chunk feerates with the RPCs the 31.0 release notes describe — `getmempoolcluster`, the chunk fields now in `getmempoolentry`, and `getmempoolfeeratediagram` for the whole mempool; (c) submit a zero-fee parent plus child with `submitpackage`, then try the parent alone; (d) extend a chain until you hit the cluster limit. Record every rejection message and map it to Bitcoin Core's `doc/policy/` and the 31.0 release notes — *Mastering Bitcoin* ch. 9 predates cluster mempool, so list what changed. *(~4 h · Bitcoin Core policy docs; Mastering Bitcoin ch. 9; Bitcoin Optech: Cluster mempool and the 31.0 release notes; Bitcoin Core release notes (Section 12))*
5. **Eclipse-attack threat model** — From Heilman et al.'s eclipse-attack paper (a reading in Chaincode's P2P session), list the attacker's steps and resources. For each step, name the Bitcoin Core countermeasure — address-manager bucketing by netgroup (and ASMap), feeler and block-relay-only connections, anchor connections kept across restarts, eviction protection, BIP 324 encryption — and find the source file that implements it. Deliverable: a three-column table (attack step → mitigation → file). *(~2.5 h · Chaincode seminar: P2P (eclipse-attack paper); Bitcoin Core connection types; BIP 324; Bitcoin Developer Guide: P2P Network)*

**🏗️ Mini-project — Compact-Block Reconstruction Monitor:** Run your mainnet node (pruned is fine) with `-debug=cmpctblock` for a week, and write a Python pipeline that parses the "Successfully reconstructed block … txn prefilled, … txn from mempool (incl at least … from extra pool) and … txn (… bytes) requested" log lines, joins them with RPC block data (tx count, size, coinbase tag → pool) and your mempool size at arrival, and reports: the share of blocks needing a `getblocktxn` round trip, the distribution of missing transactions and bytes, and which pools' blocks miss most. Deliverable: `projects/btc/06-cmpct-monitor/` (notebook plus a one-page memo with one falsifiable hypothesis about the cause — e.g., policy divergence or out-of-band transactions — and how you would test it). Success: ≥ 500 blocks analyzed; every number traces back to a log line; all plots regenerate from the raw logs. *(~8 h plus a week of passive logging · BIP 152; Mastering Bitcoin ch. 10 (Compact Block Relay))*
