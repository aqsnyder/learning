# Lightning Network

## Why This Section Matters

Lightning is Bitcoin's Layer 2 scaling solution. It enables instant, low-fee payments by creating payment channels between nodes.

## Prerequisites

- [Section 04 — Transactions and Script](../04-transactions-and-scripting/README.md)
- [Section 06 — Network and P2P](../06-network-and-p2p/README.md)

## 🎯 Learning Objectives

After this section you can:
- Walk through a channel's lifecycle — funding, asymmetric commitments, revocation, cooperative and force close — and identify every on-chain transaction and output.
- Trace an HTLC across multiple hops, computing the forwarded amount, fee and CLTV expiry at each hop.
- Decode a BOLT 11 invoice by hand and explain how the payment hash and preimage give proof of payment.
- Model payment success under liquidity uncertainty and use the model to rank routes.
- Run a multi-implementation regtest Lightning network and drive it from the CLI and an API.

4. **Optech: HTLC and CLTV expiry delta** — The two clauses of an HTLC, and why each hop needs its own expiry margin.

7. **Optech: Offers and Splicing** — Catch up on what changed after the book.

## 🛠️ Practice

1. **Stand up a lab network** — In Polar (or the book's docker-compose network: Alice on LND, Bob on Core Lightning, Chan on Eclair, Dina on LND), open Alice→Bob→Chan→Dina channels and pay a Dina invoice from Alice. On the regtest bitcoind, decode each funding transaction and identify the 2-of-2 output and its script type. Done when you can point to the funding outpoint of every channel in `listchannels` (or each implementation's equivalent). *(~2 h · Mastering the Lightning Network ch. 4; Polar (Section 12))*
2. **HTLC arithmetic** — Alice pays Dina 100,000 sat via Bob (outgoing policy: base fee 1,000 msat, 100 ppm, `cltv_expiry_delta` 40) and Chan (base 0, 500 ppm, delta 80); Dina's invoice asks for a final CLTV delta of 18; the current height is 1,000. Compute, for each hop, the amount and CLTV expiry of the HTLC it receives (each node charges its fee on the amount it forwards). Write out the offered-HTLC script and enumerate its spending paths (preimage, timeout, revocation). Check your numbers by setting the same policies in your lab and building the route with LND's `buildroute` (compare expiries relative to the current height). *(~2 h · Mastering the Lightning Network chs. 8–9; Poon–Dryja whitepaper; BOLT #2 and BOLT #3; Bitcoin Optech: HTLC and CLTV expiry delta)*
3. **Decode a BOLT 11 invoice by hand** — Create an invoice on a regtest node (`lnbcrt…`), bech32-decode it with your section-01 code (ignoring the 90-character limit), parse the amount multiplier, timestamp and tagged fields (`p`, `s`, `d`, `x`, `c`, …), and recover the payee's node key from the recoverable signature. Done when every field matches `lncli decodepayreq` and the recovered key equals the node's identity public key. *(~2.5 h · Mastering the Lightning Network ch. 15; BOLT specifications (BOLT #11))*
4. **Pay-per-reading instrument** — Write a small Python service that, for each measurement request, creates an invoice through LND's REST API and returns the reading — from an STM32 ADC over USB-serial, or a simulated sensor — only after the invoice settles; pay it from another lab node and log (payment_hash, preimage, reading) as a receipt. Stretch: put the endpoint behind Aperture (L402) as described in the Lightning Labs documentation. *(~3 h · Lightning Labs documentation (Builder's Guide); Mastering the Lightning Network ch. 15)*
5. **Force-close forensics** — Force-close a channel with balance on both sides and decode the commitment transaction: find the to_local output (revocation key or `to_self_delay` CSV path), to_remote, and any anchor outputs; compute the height at which to_local becomes sweepable and watch the sweep happen. Account for every satoshi of channel capacity from funding to final sweeps (balances, commitment fee, anchors, sweep fees). *(~3 h · Mastering the Lightning Network ch. 7; Mastering Bitcoin ch. 14; BOLT #3)*

**🏗️ Mini-project — Route-Reliability Experiment:** Build a regtest network of ≥ 6 nodes using at least two implementations, and open channels with uniformly random initial balances (random push amounts). Use LND's `buildroute`/`sendtoroute` to send ≥ 1,000 single-path payments over fixed 2–3-hop routes, with amounts from 1 % to 90 % of channel capacity, recording successes and failure codes. Compare with the uniform-liquidity model from *Mastering the Lightning Network* ch. 12, P(a) = (c + 1 − a)/(c + 1) for each channel whose balance the sender doesn't know, multiplied along the route. Deliverable: `projects/btc/07-route-reliability/` (driver script, notebook, one-page write-up). Success: measured success rates fall inside the model's 95 % binomial interval in most amount bins, and every systematic deviation is explained (channel reserve, fees, HTLC limits). *(~12 h · Mastering the Lightning Network ch. 12; Pickhardt & Richter, "Optimally Reliable & Cheap Payment Flows")*
